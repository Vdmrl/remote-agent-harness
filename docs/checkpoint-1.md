# ЧП1 — план реализации и демонстрации

Статус: запланировано, ничего из перечисленного ниже ещё не проверено исполнением.
Целевая демонстрация: 2026-11-06, исходя из указанного пользователем срока.
Контекст и источники: [project-plan.md](project-plan.md).

## Что считаем готовым

- Из чистого клона на Linux сервер собирается и запускается одной командой Compose; проверки здоровья реальные.
- Десктоп-клиент подключается по адресу и токену, отправляет задачу и показывает события; тот же сценарий доступен через CLI.
- Настоящая модель вызывает инструменты собственного харнеса; команды исполняются в сандбоксе.
- Два контракта v0 имеют машиночитаемые схемы; проверены завершение, ошибки, таймаут и отмена.
- Первые ADR объясняют реализованные решения и отмечают открытый выбор монтирования.
- Раннер запускает задачи Б1–Б5, проверяет итоговые файлы и сохраняет честные результаты.

## Объём БАФ

Строка ЧП1 не уточняет, достаточно ли простых задач Б1–Б5. Поэтому наш целевой объём — 15 задач: пять функций × три уровня. Пять простых задач — первый промежуточный результат, а не объявление всего ЧП1 завершённым. Если к показу есть провалы, сохраняем их и показываем фактическое покрытие.

Полностью оформленный курсовой пример только один; остальные фикстуры и чекеры готовим по [каталогу](https://github.com/deeppavlov/agentic-course-itmo/blob/main/projects/templates/track-a-agent-runtime/baf/catalog.yaml). Эталоны и чекеры не доступны агенту. Результат mock-прогона не считается качеством пары с настоящей LLM.

Первый сквозной путь — C1-1. Пакеты выполняем последовательно: раннер использует уже стабилизированные в C1-3 протоколы. При изменении схем повторяем контрактные проверки.

До показа один день, готового кода нет, Docker Engine недоступен, модель ещё не выбрана. План задаёт целевой объём, но не обещает завершение к сроку без проверки этих зависимостей. Приоритет: рабочий сквозной путь, реальный вызов инструментов, пять simple-задач в раннере, затем остальные десять и финальная проверка. Невыполненное остаётся явно отмеченным.

ADR по харнесу, Docker-доступу и протоколам пишем черновиками уже во время C1-1/C1-2; C1-5 сверяет их с итоговым кодом. Выбор монтирования остаётся proposed до прототипа. Клиентский и сандбоксный контракты, модель ошибок и идентификаторы имеют один источник в contracts/.

## Что закладываем в сквозной путь

Предлагаемые ограничения первой версии:

- Сандбокс не получает ключ модели или Docker socket; команды не исполняются в gateway/harness.
- Отдельный контейнер с непривилегированным пользователем; cap-drop, no-new-privileges, read-only root; записываемые /work и /tmp ограничены по размеру. Задаём CPU/RAM/PIDs и таймауты.
- Сеть сандбокса выключена; служебная сеть сервисов отдельно. Публичный вход только через gateway, внутренние операции защищены служебной авторизацией.
- Путь проверяется на границе инструментов, включая выход через симлинки; сначала готовим безопасную рабочую папку, затем запускаем инструменты.
- Отмена уничтожает контейнер с деревом процессов. В первой версии отменённая сессия требует нового сандбокса; клиентская папка никогда не является целью удаления.
- Идентификаторы запросов защищают от повторного exec; у операции один итог и ограничение времени. Сбой транспорта не вызывает слепой повтор команды с побочными эффектами.
- Первый набор проверок: успешная команда, ненулевой exit, таймаут, cancel с дочерним процессом, повтор request_id, неверный токен, выход за /work, отсутствие секрета и очистка.

Это базовая защита первой реализации. Полный набор атак, режимы сети и проверки дисковых лимитов расширяем к ЧП2; их прохождение сейчас не утверждаем.

Для БАФ предлагаем ограниченный по размеру tmpfs /work внутри сандбокса. Runner передаёт только фикстуру через sandbox-manager; артефакты извлекаются операцией collect до release. При cancel содержимое tmpfs может быть потеряно — это фиксируется в исходе запуска и клиентском сообщении. Журнал событий хранится вне сандбокса без ключей и содержимого пользовательских файлов. Это тестовое наполнение /work, а не монтирование локальной папки пользователя. Настоящее монтирование проверяется отдельным сценарием на двух машинах в ЧП2; для него отдельно определяем сохранность файлов при обрыве и отмене.

В протоколе харнес ↔ сандбокс явно описываем provision, exec, events, result, collect, release/cancel. Модель ошибок различает ошибку команды, таймаут, ошибку сандбокса и транспортный сбой; у каждого класса своя политика повторов. Для exec с неизвестным исходом сначала запрашиваем состояние операции, а не запускаем её повторно.

## Первые ADR

Планируем четыре документа: собственный харнес; запуск и границы Docker-сандбокса; оба протокола и модель сессий; сравнение механизмов монтирования. Сетевая политика и окончательный выбор пары получат отдельные ADR по мере реализации и экспериментов. У предлагаемого решения явный статус proposed; accepted означает, что решение принято, но само по себе не доказывает прохождение тестов.

## Как показываем результат

1. Показать архитектуру и один переход агентного цикла в коде.
2. Поднять сервер и подключить десктоп-клиент.
3. Дать агенту задачу: найти значение в файле и записать результат в новый файл. Показать вызовы инструментов и содержимое артефакта.
4. Запустить долгую команду, отменить её и показать отсутствие контейнера и дочерних процессов.
5. Показать отчёт Б1–Б5 и сохранённый JSONL; отдельно назвать незакрытые проверки.
6. Объяснить решения в ADR и ближайший риск: настоящее удалённое монтирование.
