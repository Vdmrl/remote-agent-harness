# remote-agent-harness — план проекта

Дата: 2026-11-05. Репозиторий: [Vdmrl/remote-agent-harness](https://github.com/Vdmrl/remote-agent-harness), public.
Пользователь поручил реализовать ЧП1 и публиковать законченные шаги отдельными Conventional Commits.

## Что показывает проект

Собственный харнес агента: агентный цикл, вызовы инструментов, сборка контекста, обработка ошибок и ограничение выполнения. Команды выполняются в Docker-сандбоксах через отдельный протокол. В итоговой системе десктоп-клиент предоставляет локальную папку удалённому агенту через настоящее монтирование.

Предлагаемое описание GitHub:

> Agent harness with remote tool execution, local workspace mounting, and reproducible evaluations.

При публикации README будет отдельно показывать реализованные возможности и roadmap: описание цели не считается доказательством работающего монтирования.

## Решения для начала разработки

Это проектные предложения, а не требования курса и не уже принятые ADR.

| Область | Предложение | Зачем |
|---|---|---|
| Харнес | Свой небольшой Python-цикл без агентного фреймворка | Показать собственную реализацию и уметь объяснить каждый переход |
| API сервисов | FastAPI; HTTP/JSON; SSE для событий клиента | Один стек, явные контракты и возможность повторного чтения событий |
| Запуск | Четыре Compose-сервиса: gateway, harness, sandbox-manager, llm-proxy | Сохранить границы из шаблона; не добавлять брокер, Kubernetes и БД без необходимости |
| Сандбоксы | Docker SDK; отдельный контейнер на сессию | Изоляция рабочего каталога и понятная очистка ресурсов |
| Docker-доступ | Только sandbox-manager получает Docker socket | Сокет даёт управление хостом; риск и альтернативы фиксируются в ADR |
| Клиент | Python: простой Tkinter GUI и CLI на общем сетевом коде | Выполнить десктопный сценарий и автоматизировать проверки без второго языка |
| Модели | По запросу пользователя gpt-6-luna через inference-адаптер Codex CLI; также HTTP API и mock | ChatGPT-вход уже проверен; ключи и учётные данные остаются вне репозитория и сандбоксов. Допуск модели по правилам курса проверяется отдельно |
| Тестирование | Mock/replay для повторяемых проверок; отдельный запуск с настоящей LLM | Не смешивать работоспособность инфраструктуры с качеством агента |
| Зависимости | pyproject.toml и lock-файл; версии образов закреплены | Повторяемая сборка и понятный состав проекта |

Документация выбранных компонентов: [FastAPI](https://fastapi.tiangolo.com/), [Tkinter](https://docs.python.org/3/library/tkinter.html), [Docker SDK](https://docker-py.readthedocs.io/en/stable/containers.html), [граница доверия Docker](https://docs.docker.com/engine/security/).

## Как проходит задача

```text
Desktop / CLI → Gateway → Harness → LLM proxy → Model API
                              ↓
                       Sandbox manager → Session container /work
```

Клиент видит события сессии. Харнес запрашивает инструменты через sandbox-manager; он не запускает пользовательские команды на собственном хосте. Ключ модели остаётся в llm-proxy. Итог выполнения и JSONL-трейс связаны идентификаторами сессии и запуска.

Рабочая гипотеза для ЧП1: одна активная задача в сессии, отдельный контейнер на сессию, последовательные вызовы инструментов. Параллельные сессии и восстановление после перезапуска сервера нужно уточнить отдельным решением до ЧП2.

## Этапы

| Этап | Результат | Как показываем |
|---|---|---|
| ЧП1 — сейчас | Запускаемый сервер, подключающийся клиент, выполнение в сандбоксе, контракты v0, первые ADR и раннер Б1–Б5 | Сквозная демонстрация и сохранённые результаты проверок |
| ЧП2 | Реальное монтирование между разными машинами; усиленная изоляция; CI и расширенный набор БАФ | Двусторонние изменения файлов, сценарии сбоев и воспроизводимые проверки |
| ЧП3 | Сравнение пар «харнес + LLM», выводы и материалы защиты | Матрица качества, времени и токенов со ссылками на сырые результаты |

Подробный текущий план: [checkpoint-1.md](checkpoint-1.md).

В ЧП2 входят собственные задачи по всем восьми БАФ, своя атомарная функция с тремя задачами и своя составная задача. В ЧП3 планируем три пары, фиксируя среду и версии моделей; окончательную пару выбираем по эксперименту. Замеры файловой системы и сандбоксов оформляем отдельными воспроизводимыми командами. Финальную трассировку всех A-1…A-12 сверим перед завершением ЧП2 и перед защитой.

## Что нужно решить до зависимой работы

| Вопрос | Когда нужен ответ | Что делаем до ответа |
|---|---|---|
| Endpoint и допуск модели | До итогового сравнения качества | Пробуем gpt-6-luna через локальный CLI с текущим ChatGPT-входом; mock-прогоны маркируем отдельно |
| Рабочий Linux Docker Engine | До проверки сандбокса | Проверяем окружение и запускаем Docker Desktop либо Linux-сервер |
| GitHub-авторизация на запись | До первой публикации | Репозиторий Vdmrl/remote-agent-harness создан и проверен как public; Git remote настроен |
| Регистрация сочетания харнес × сандбокс × монтирование | До фиксации архитектуры | Формулируем свой вариант и отмечаем, что уникальность пока не проверена |
| Механизм монтирования | Исследуем в ЧП1, реализуем в ЧП2 | Сравниваем SSHFS через обратный SSH-туннель, WebDAV/rclone и NFS поверх WireGuard; проверяем Windows-клиент и Linux-сервер |

Монтирование выбираем по результату короткого прототипа, а не по названию технологии. Критерии: двусторонняя видимость изменений, RO/RW, поведение при обрыве, права, очистка и сложность поддержки на двух ОС. Копирование или синхронизация папки не считаются выполнением этого требования.

## Факты окружения на момент планирования

- Исходный шаблон импортирован отдельным коммитом. Origin указывает на созданный пользователем репозиторий.
- Docker Desktop запущен; работоспособность Engine ещё проверяется. У отдельного WSL-дистрибутива Ubuntu отсутствует VHDX; его данные не меняем.
- Python, uv и Codex CLI доступны. Codex авторизован через ChatGPT; тестовый запрос к gpt-6-luna завершился успешно.
- Локальный рабочий процесс BMad настроен и исключён из Git. Пользовательские планы остаются в docs/.
